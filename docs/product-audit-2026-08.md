- [#802 — bourse seating model](https://github.com/tjorim/champagnefestival/issues/802): [owner-agreed booking/product guidance](decisions/802-booking-products-and-seating.md) covers event-owned plans, manual/partial allocation with guest counts per table for split festival bookings, optional stock, booked prices, nested included products and shared notes. The three implementation increments now provide inventory/packages, multi-room event plans, split/shared/exclusive allocations, and a combined booking/payment/quantity editor. The editor previews totals and payment differences and requires the administrator to choose which table to release before an over-allocated quantity reduction can be saved atomically. The plan itself supports adding, moving, changing guest counts and removing booking allocations from a selected table. Visitors can submit a change or cancellation request that leaves the booking active for an administrator decision; approval and reimbursement are not guaranteed — that request's organiser notification is now delivered through the durable outbox (retried on transient failure) rather than a best-effort inline send. Products carry an optional short description; a package inclusion's visibility in the visitor-facing order summary is decided entirely by whether its target product is purchasable (#1020, below) — it still counts toward stock/preparation totals either way. Booking payments are an append-only ledger (#1019): an administrator records dated transactions (a positive amount for a payment, negative for a refund, with an optional reference/note — there's no separate `kind` field) against a booking rather than editing one mutable paid total, and `amount_paid`/`payment_status` are derived from the ledger's sum rather than settable directly. The booking editor shows the chronological ledger and an "Add transaction" flow (a refund can still be linked to the specific entry it reverses via `reversed_transaction_id`, but the form relies on the entry's note/date for that rather than a picker). Admins can see total paid/due plus received/refunded/outstanding/refund-liability per edition (edition attendance stats) and the same received/refunded breakdown per person (people registrations view), then drill into the underlying ledger entries for that edition or person in an in-app modal or export the same filtered set as CSV, and compare two floor plans for a room to see added/removed/changed tables and areas. #1021 added immutable, named revisions of one event-room plan on top of that comparison: an explicit **Save revision** action snapshots the current tables/areas/room geometry (never allocations) under a concurrency-safe revision number; any two revisions, or a revision against the live draft, can be compared or restored, matched by each table/area's stable id rather than its mutable name so a rename never reads as an add+remove; and restoring previews the affected geometry and refuses (unless explicitly overridden) to delete or move a table/area that still holds a live registration or exhibitor assignment — restoring itself never touches registrations or allocations. Issue #1020 replaced the standalone `active` flag with a single `purchasable` boolean covering both standalone order availability and visitor visibility — existing active/inactive products migrated to purchasable true/false; only a purchasable product is orderable standalone, counts toward the required-product rule, and is ever named to a visitor, standalone or as a package line; a required product must be purchasable (enforced at the schema, service, and database-check-constraint layers); a hidden (`purchasable=False`) product can always be newly bundled into a package (there is no longer a separate "disabled" state that blocks this); and the unauthenticated edition/checkout responses now serialise a slim visitor-safe product shape (no `stock`) that excludes hidden products entirely, including stripping any inclusion edge pointing at one, while admin endpoints and a matching MCP `*_product` tool set keep the full shape. Capsule-exchange companion policy remains the only undecided scope; #802 stays open until that rule is confirmed or split out.
