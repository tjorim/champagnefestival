# Architecture

How the code is organised. The same layout is used in champagnefestival, daynest, travel and worktime, so a developer who
knows one of them finds things in the same place in the others. Only the feature (domain) folders differ.

## Frontend (`frontend/src/`)

```
main.tsx, sw.ts         entry point and service-worker entry; nothing else lives loose in src/
app/                    bootstrap and app shell: providers, router (route tree, standalone route shells), layout, theme
features/<domain>/      one folder per business domain: pages (*Page.tsx), components used only there, hooks,
                        feature-only helpers and API calls
components/             shared UI used by two or more features; components/ui/ holds the design-system primitives
hooks/                  shared hooks used by two or more features
lib/                    framework-agnostic helpers and the HTTP client (lib/api/); no `utils/` folder
mocks/                  MSW handlers and fixtures (fixtures are typed with the generated API types)
config/                 runtime configuration and constants
types/                  UI-only types (never API shapes)
paraglide/              compiled messages (generated)
styles/                 global CSS (tailwind.css, fonts.css, print.css)
sw/                     service-worker modules imported by sw.ts
api-schema/             generated by Orval, never edited   api-types.ts   the single import point for API shapes
```

Rules:

- A folder under `features/` is named after the product domain, in kebab-case. Split one that grows past about 40 files
  into sub-folders by sub-area (`features/admin/` does: `shell`, `shared`, `people`, `registrations`, `editions`,
  `venue`, `content`, `insights`).
- Keep a source file under about 800 lines. When a screen grows past that, split it along its own seams into a sub-folder
  next to it, named after the screen (`features/admin/venue/layout/` for `LayoutEditor.tsx`): sub-components for the
  canvas, inspector and dialogs, a hook for the state and handlers they share, and plain modules for helpers. The screen
  file keeps its default export, so lazy-section imports and the bundle budgets do not change. Generated files are the
  only exception.
- Code used by one feature stays in that feature. Move it to `components/`, `hooks/` or `lib/` only when a second feature
  needs it.
- Import across folders with the `@/` alias (`@/features/admin/people/PeopleSection`); use relative imports only inside
  one feature folder (at most one `../`).
- A feature does not import another feature, with three deliberate exceptions: `app/` composes the pages of every
  feature (route components and the route tree), `features/site/` embeds the registration modal and the maintenance page,
  and `features/admin/shell/` embeds the signage section. Anything else two features need goes to a shared folder.
- API shapes come from `@/api-types` (generated types). Never declare an API response type by hand.
- Component files are `PascalCase.tsx`, hooks `useThing.ts`, other modules `camelCase.ts`.
- Tests live in `frontend/tests/` and mirror the `src/` path (`src/features/site/Countdown.tsx` is covered by
  `tests/features/site/Countdown.test.tsx`); shared helpers are in `tests/utils/`, global setup is `tests/setup.ts`.
  End-to-end specs are in `frontend/e2e/`.

### Exceptions

- `src/sw.ts` stays at the top of `src/` because `vite.sw.config.ts` and `tsconfig.sw.json` point at it; the modules it
  imports live in `src/sw/`.
- `components/admin/` holds the admin building blocks (editor dialog, fields, row actions, empty state, theme scope) that
  the public pages, the signage editor and the admin sections all use. It is a shared folder, not an admin feature.
- `lib/` has sub-folders by topic: `api/` (HTTP calls and error mapping), `collections/` (TanStack DB collections and
  their cache), `editions/` (edition, event and poll helpers), `query/` (query keys and invalidation), `venue/` (floor
  plan and map helpers) and `format/`.

## Where does new code go?

- A new page or screen: `features/<domain>/<Name>Page.tsx`, lazy-loaded from `app/StandaloneRoutes.tsx` and registered
  in `app/router.tsx`.
- A component only one feature uses: that feature's folder. A second feature needs it: `components/`.
- A design-system primitive (a Base UI / shadcn wrapper): `components/ui/`, recorded in `ui-maintenance.json`.
- A hook or helper only one feature uses: that feature's folder. Shared: `hooks/` or `lib/<topic>/`.
- An API call: next to the feature that owns it; calls used by several features go to `lib/api/`.
- A provider, router change or layout piece: `app/`.
- MSW handlers and fixtures: `mocks/`. The authenticated admin handlers are one module per domain in
  `mocks/handlers/admin/` (`state.ts` holds the mutable stores, `auth.ts` the token and scenario checks); `index.ts`
  concatenates them in a fixed order because MSW takes the first match, so a literal route such as `/api/editions/stats`
  must stay ahead of its `/:id` sibling. Constants and runtime configuration: `config/`.
- A test: `tests/` at the same path as the file it covers; a test helper: `tests/utils/`.

## Backend (`backend/app/`)

```
main.py                 app assembly: middleware, router registration, lifespan; nothing else
openapi_export.py       writes frontend/openapi.json (`uv run python -m app.openapi_export`)
version.py              the release version read from /VERSION
routers/                the HTTP layer, one module per domain; thin: validate, call a service, return a response model
services/              business logic shared by the routers and the MCP tools, one module per domain (`*_service.py` and
                        topic modules such as `poll_*`, `member_mail*`, `public_render*`, `signage_*`)
  live/                 live-update infrastructure: in-process bus, Postgres NOTIFY publication and LISTEN relays, the
                        domain-action to TanStack-key mapping
  serializers.py        the response builders (`*_to_out`) that turn models into response schemas
  worker.py, maintenance.py   the outbox worker and the housekeeping command (`python -m app.services.worker`, `python -m app.services.maintenance housekeeping`)
  email_service, member_mail*, push_*, composer_*, visitor_session, audit_service   the former loose domain modules
models/                 SQLAlchemy models, one module per domain; `base.py` has the shared helpers, `__init__` imports
                        every module (Alembic needs them all) and re-exports the names
schemas/                Pydantic request and response models, one module per domain; `base.py` has RequestModel and
                        ResponseModel, `types.py` the constrained value types, `signage.py` the signage canvas contracts,
                        `openapi_responses.py` the OpenAPI declarations for file downloads
core/                   settings, OIDC and bearer auth, shared FastAPI dependencies (pagination, sorting), rate and request
                        limits, observability, translation vocabulary, anti-spam, ids, CSV and geometry helpers
db/                     engine and session (`session.py`), the declarative base (`base.py`), query helpers (`queries.py`),
                        the SQLite compatibility layer and the SQL bootstrap statements for search and the payment ledger
mcp/                    the MCP server (`server.py`: the FastMCP assembly and tool registration), `tools/` (the tool
                        methods of `ChampagneFestivalMcpBackend`, one mixin per domain over the shared caller resolution
                        in `tools/base.py`), the tier modules (`public`, `seating`, `orders`, `check_in`, `delivery`),
                        `admin/` (one module per domain) and MCP auth, capabilities and middleware
middleware/             ASGI middleware: CORS, trusted hosts and the general rate limiter (`setup.py`), Server-Timing
                        and the slow-request log (`request_timing.py`)
```

Tests live in `backend/tests/` and mirror this tree (`tests/routers`, `tests/services`, `tests/core`, `tests/db`,
`tests/middleware`, `tests/schemas`, `tests/mcp` with `tests/mcp/admin`); `conftest.py`, `helpers.py`,
`poll_helpers.py` and `fixtures/` are shared. The `*_migration` tests (they find `alembic/` relative to `tests/`), the
OpenAPI snapshot, the response-model and contract scans, and the API tests that span several domains (bulk create,
translations, account unification, poll orders, ...) stay at the top. Sibling-test imports are package imports
(`from tests.routers.test_visitor_sessions import ...`).

Rules: every JSON route declares a response model; routers do not touch the database directly; code used by one domain
stays in that domain's modules. Dependencies point downwards: `routers` and `mcp` -> `services` -> `schemas`, `models` ->
`core`, `db`. `core`, `db`, `models` and `schemas` do not import `routers` or `mcp`. The known upward edges are
`core/ratelimit.py` (reads the rate-limit table through `models`), `db/queries.py` (the `PersonRolePeriod` filters),
`db/sqlite_compat.py` (imports `services/live` and `services/public_render_cache`: the SQLite stand-in for
LISTEN/NOTIFY), `schemas/composer.py` (imports `services/composer_content.py`, the composer's locale and push-payload
validation) and `schemas/` (the poll limits from `models`); `models/orders.py` imports two schemas under `TYPE_CHECKING`
only.

Naming: `from app.models import X` and `from app.schemas import X` keep working through the package re-exports (explicit
`__all__`); new code may import the submodule (`from app.schemas.registrations import RegistrationOut`). Models that
refer to each other only in annotations import each other under `TYPE_CHECKING` (the module files use
`from __future__ import annotations`). The `services/` modules are still one flat folder of 83 modules; grouping the
`poll_*`, `member_*`, `public_render*` and `signage_*` families into sub-packages is a later, mechanical step.

### Where does new backend code go?

- A new endpoint: `routers/<domain>.py` (thin), its operation in `services/<domain>_service.py`, request/response models
  in `schemas/<domain>.py`, tables in `models/<domain>.py` plus an Alembic revision; add the new model module to
  `models/__init__.py` and the schemas to `schemas/__init__.py`.
- An MCP tool: `mcp/admin/<domain>.py` (or a tier module), calling the same service the router calls; register it in
  `mcp/tools/<domain>.py` (the thin method that checks the role and delegates) and in `ChampagneFestivalMcpBackend`'s tool
  list in `mcp/server.py`.
- Something every domain needs and that knows nothing of a domain (settings, auth, limits, ids): `core/`.
- Something that reads or writes the engine, session or schema bootstrap: `db/`. ASGI plumbing: `middleware/`.
- A background job: a handler in `services/`, registered in `services/worker.py`.

### Entry points

The commands that start something are modules run with `python -m`: `app.services.worker` (the Dockerfile `worker` target), `app.services.maintenance housekeeping` (the scheduled unit), `app.mcp.server` (the stdio MCP server) and `app.openapi_export`. Nothing forwards from an older path.

Logger names that come from `__name__` follow the module (for example `app.middleware.setup`,
`app.core.observability`, `app.mcp.server`, `app.services.live.listener`). The route and model docstrings that end up in
`frontend/openapi.json` keep their old text, even where it names a module that moved (the push route still says
`app.config.Settings`), because changing it would change the committed API document.
