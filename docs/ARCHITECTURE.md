# Architecture

How the code is organised. The same layout is used in champagnefestival, daynest, travel and worktime, so a developer who
knows one of them finds things in the same place in the others. Only the feature (domain) folders differ.

## Frontend (`frontend/src/`)

```
main.tsx, sw.ts         entry point and service-worker entry; nothing else lives loose in src/
app/                    bootstrap and app shell: providers, router (route tree, standalone route shells), layout, theme
features/<domain>/      one folder per business domain: pages (*Page.tsx), components used only there, hooks,
                        feature-only helpers and API calls
components/             shared UI used by two or more features; components/ui/ holds the design-system primitives
hooks/                  shared hooks used by two or more features
lib/                    framework-agnostic helpers and the HTTP client (lib/api/); no `utils/` folder
mocks/                  MSW handlers and fixtures (fixtures are typed with the generated API types)
config/                 runtime configuration and constants
types/                  UI-only types (never API shapes)
paraglide/              compiled messages (generated)
styles/                 global CSS (tailwind.css, fonts.css, print.css)
sw/                     service-worker modules imported by sw.ts
api-schema/             generated by Orval, never edited   api-types.ts   the single import point for API shapes
```

Rules:

- A folder under `features/` is named after the product domain, in kebab-case. Split one that grows past about 40 files
  into sub-folders by sub-area (`features/admin/` does: `shell`, `shared`, `people`, `registrations`, `editions`,
  `venue`, `content`, `insights`).
- Code used by one feature stays in that feature. Move it to `components/`, `hooks/` or `lib/` only when a second feature
  needs it.
- Import across folders with the `@/` alias (`@/features/admin/people/PeopleSection`); use relative imports only inside
  one feature folder (at most one `../`).
- A feature does not import another feature, with three deliberate exceptions: `app/` composes the pages of every
  feature (route components and the route tree), `features/site/` embeds the registration modal and the maintenance page,
  and `features/admin/shell/` embeds the signage section. Anything else two features need goes to a shared folder.
- API shapes come from `@/api-types` (generated types). Never declare an API response type by hand.
- Component files are `PascalCase.tsx`, hooks `useThing.ts`, other modules `camelCase.ts`.
- Tests live in `frontend/tests/` and mirror the `src/` path (`src/features/site/Countdown.tsx` is covered by
  `tests/features/site/Countdown.test.tsx`); shared helpers are in `tests/utils/`, global setup is `tests/setup.ts`.
  End-to-end specs are in `frontend/e2e/`.

### Exceptions

- `src/sw.ts` stays at the top of `src/` because `vite.sw.config.ts` and `tsconfig.sw.json` point at it; the modules it
  imports live in `src/sw/`.
- `components/admin/` holds the admin building blocks (editor dialog, fields, row actions, empty state, theme scope) that
  the public pages, the signage editor and the admin sections all use. It is a shared folder, not an admin feature.
- `lib/` has sub-folders by topic: `api/` (HTTP calls and error mapping), `collections/` (TanStack DB collections and
  their cache), `editions/` (edition, event and poll helpers), `query/` (query keys and invalidation), `venue/` (floor
  plan and map helpers) and `format/`.

## Where does new code go?

- A new page or screen: `features/<domain>/<Name>Page.tsx`, lazy-loaded from `app/StandaloneRoutes.tsx` and registered
  in `app/router.tsx`.
- A component only one feature uses: that feature's folder. A second feature needs it: `components/`.
- A design-system primitive (a Base UI / shadcn wrapper): `components/ui/`, recorded in `ui-maintenance.json`.
- A hook or helper only one feature uses: that feature's folder. Shared: `hooks/` or `lib/<topic>/`.
- An API call: next to the feature that owns it; calls used by several features go to `lib/api/`.
- A provider, router change or layout piece: `app/`.
- MSW handlers and fixtures: `mocks/`. Constants and runtime configuration: `config/`.
- A test: `tests/` at the same path as the file it covers; a test helper: `tests/utils/`.

## Backend (`backend/app/`)

The backend keeps its current layout for now (`routers/`, `services/`, `mcp/`, `live/` and flat modules such as
`models.py` and `schemas.py`). The shared target, applied to all four apps in a later step, is `main.py`, `core/`, `db/`,
`models/`, `schemas/`, `routers/`, `services/`, `mcp/` and `middleware/`.
